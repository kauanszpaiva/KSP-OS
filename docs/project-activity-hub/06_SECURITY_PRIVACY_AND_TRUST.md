# 06 — Security, Privacy, and Trust

Status: **Complete** (planning-only) · 2026-07-23

## Foundational principle: external content is never trusted instructions

Every piece of text this system ingests from an external system — commit messages, PR titles/descriptions, issue/comment bodies, webhook payload fields, provider log lines — is **untrusted data**, full stop. It may be displayed, summarized, correlated (with confidence scoring), or stored (redacted, retention-limited). It must **never** be interpreted as an instruction to any AI component of this system or any downstream automation. This holds even inside AI-generated summaries: an AI summarizer reading a batch of commit messages to produce a weekly report must be constrained (via system prompt design at implementation time, and verified by the prompt-injection test cases in `08_TEST_AND_VERIFICATION_PLAN.md`) to *describe* that content, never *obey* it. No action in this system — not a notification, not a correlation, not (once Phase 7 exists) a controlled action — is ever triggered because a commit message, issue body, PR description, webhook payload, or log line said to do something.

## Retention matrix

| Data category | Default retention | Rationale |
|---|---|---|
| Raw webhook payloads (`external_event_deliveries.redacted_payload`) | 1 year (GitHub/Vercel), 90 days (Supabase) | Debugging window without indefinite log accumulation; matches `01_INTEGRATION_CAPABILITY_MATRIX.md`'s volume-conscious defaults |
| Normalized events (`project_activity_events`) | Indefinite | This is the product-facing history — the whole point of the system |
| AI prompts | **Never stored** | Explicit PDF principle; only `objective`/`sanitized_summary` are stored, never a full prompt |
| AI responses | **Never stored in full** | Same — only sanitized summaries and structured evidence (files touched, tests run, commits) |
| AI summaries (`ai_agent_sessions.sanitized_summary`, `activity_summary_reports.narrative_summary`) | 1 year | These are KSP-authored-adjacent derived content, not raw provider data, and are actively useful for longer |
| AI tool events (`ai_agent_session_events`) | 90 days | Highest-granularity AI data — "avoid storing complete terminal sessions" principle |
| Terminal/command output | Summarized only, never full output stored | Explicit PDF principle |
| Build logs | Not stored beyond a failure summary + provider link | Explicit PDF caution against "unlimited log ingestion"; Vercel's own retention (1hr–3day by plan) means near-real-time capture matters more than long-term storage anyway |
| Database logs | Not ingested beyond Auth Audit Logs (queried live from Supabase, not copied) and migration-run summaries | Avoids duplicating Supabase's own log retention |
| Test output | Summarized (pass/fail counts, failure messages) — not full stdout | Same "avoid unlimited log copies" principle |
| Files changed | File paths + change type stored; full diffs **not** stored by default | Balances evidence value against payload size/PII risk |
| Commit messages | Stored as-is (already public/internal within the org's own repos) but always treated as untrusted text for AI purposes | Not secret, but never trusted as instructions |
| Pull-request content | Title/description stored; full review-comment threads summarized, not fully mirrored | Avoids duplicating GitHub as a system of record |
| User identities (`external_actor_identities`) | Indefinite | Needed for long-term provenance; low sensitivity (username-level, not credential-level) |
| Access tokens / refresh tokens | **Never stored in the ledger** — only in `integration_connections`' existing metadata-only shape (no token-value column, per `00_CURRENT_SYSTEM_AUDIT.md` §18) | Matches the repo's existing, already-correct pattern |
| Provider installation metadata | Indefinite | Low sensitivity, operationally necessary |
| Cost records | Indefinite | Financially relevant, low sensitivity beyond existing Finance-module handling |
| Error records | Same as their parent category (raw delivery / session event retention) | No special-cased longer retention for errors alone |
| Security records (`security` event family) | Indefinite | Security-relevant history should not be time-limited |

**Default principles applied throughout**: never store secrets; never store `.env` contents; never store access/refresh tokens in the ledger; never expose provider credentials to client-side code; avoid storing complete AI conversations; avoid storing complete terminal sessions; avoid copying unlimited provider logs; prefer hashes, summaries, references, and external links over raw copies. Stricter retention for sensitive clients and legal/operational holds are **not** designed in this phase — flagged in `12_OPEN_QUESTIONS_AND_DECISIONS.md` as a future need, not silently assumed unnecessary.

## Visibility rules

What a user can view is determined by the same four axes already governing every other KSP OS module — organization, project (via `project_memberships`/`is_executive`), role, and classification (`data_classification` — already an existing enum used by `audit_events`/`request_triage`) — plus one new axis specific to this module: **integration permission** (whether a given `project_integration_mappings` row itself is visible, independent of the events it produces, gated the same way as the mapping's own RLS policy in `04_DATA_MODEL.md` §04.1). No client-sensitivity-based visibility rule is needed in this phase, since the Hub is explicitly internal-only (`02_PRODUCT_SCOPE.md`'s Non-goals) — client sensitivity becomes relevant only if a future, separately-scoped client-safe subset is ever built.
