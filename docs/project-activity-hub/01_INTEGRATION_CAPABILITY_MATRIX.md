# 01 — Integration Capability Matrix

Status: **Complete** (research-only) · Researched: 2026-07-23

This matrix records the *current, officially documented* capabilities of every provider the Project Activity Hub would connect to. Findings come from live research (WebSearch/WebFetch against official docs, plus one case — GitHub — cross-verified against the open-source `github/docs` repository) conducted on 2026-07-23, not from model memory. Where a claim could not be verified against a primary source, it is explicitly labeled **UNKNOWN**. Confidence levels (High/Medium/Low) reflect how many independent sources corroborated a finding and whether a primary-source page was actually fetched vs. reconstructed from search snippets.

**Classification legend** (used in the "Class" column below):
- **Proven** — directly confirmed against official docs, stable/GA.
- **Plan-dependent** — capability exists but is gated behind a specific account/plan tier.
- **Beta/Preview** — explicitly labeled non-GA by the provider.
- **Unsupported** — the specific thing KSP wants doesn't exist; a fallback is required.
- **Needs-wrapper** — capability exists only via a CLI/SDK wrapper, not a raw API.
- **Downstream-only** — cannot observe the activity directly; must infer it from a *different* system's evidence (e.g., a GitHub PR a Codex cloud task opened).
- **Unknown** — genuinely unverified; flagged for direct hands-on confirmation before any implementation decision relies on it.

**Access note**: Direct `WebFetch` of `docs.github.com`, `vercel.com/docs`, `developers.openai.com`, `platform.openai.com`, and `help.openai.com` returned HTTP 403 (bot protection) in this environment for every attempt. GitHub findings were cross-verified against the public `raw.githubusercontent.com/github/docs` markdown source, giving High confidence. Supabase findings were similarly cross-verified against `raw.githubusercontent.com/supabase/supabase`. Vercel and OpenAI findings rely on WebSearch-returned snippets corroborated across 3+ independent queries per finding — treat exact numeric limits from those two providers as **Medium confidence** and re-verify directly (logged into each dashboard) before finalizing any cost/rate-limit-dependent design decision.

### Cross-cutting notes carried into later documents

1. **GitHub's security/reliability posture is materially more mature and verifiable than Vercel's** (SHA-256 vs. SHA-1 signatures, a documented 3-day replay window vs. no documented Vercel retry mechanism at all). KSP's own reliability engineering (dead-lettering, idempotency, reconciliation) should be invested more heavily on the Vercel ingestion path — see `06_SECURITY_PRIVACY_AND_TRUST.md`.
2. **Codex structurally differs from Claude Code** in three ways that need distinct adapter handling, not an assumed-parity design: (a) Codex's structured events are an *observation feed*, not an extensible hook/interception mechanism like Claude Code's; (b) Codex's official SDK is TypeScript-only vs. Anthropic's broader language coverage; (c) Codex cloud is a more fully-realized "hosted task with CLI-scriptable status" product than anything typical for Claude Code, and needs its own adapter category rather than being forced into the same shape as local Claude Code sessions.
3. **The MCP identity-auditing gap (X12) is provider-agnostic** — it is a property of the shared MCP spec, not a Codex-vs-Claude difference, and must be solved once in KSP's own MCP server design, not per-provider.
4. **Every "no fallback exists" finding above is a genuine ceiling, not a research gap**: Supabase Platform Audit Logs on Pro tier (S3), Vercel exact rate limits (V8), and Codex cloud's third-party REST API (X3) are all things that either require a plan upgrade, direct support contact, or accepting a downstream-only design — these should be surfaced explicitly in `12_OPEN_QUESTIONS_AND_DECISIONS.md`, not silently designed around.
